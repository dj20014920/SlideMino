# SlideMino 방해요소(Obstacle) 시스템 — 배포 전 초심층 종합 코드리뷰

당신은 시니어 소프트웨어 엔지니어, UX 디자이너, QA 엔지니어, 보안 감사자, 그리고 2048 게임 헤비 유저의 역할을 동시에 수행하는 최종 리뷰어입니다. 아래 코드베이스 변경사항을 **배포 승인** 관점에서 다각도로 분석해주세요.

---

## 📦 프로젝트 개요

- **프로젝트명**: SlideMino
- **유형**: 2048 변형 퍼즐 게임 (React + TypeScript + Vite + Capacitor)
- **주요 변경**: 5종 방해요소(Obstacle) 시스템 신규 도입
- **변경 규모**: 5개 핵심 파일, +2,228 라인 / -40 라인
- **테스트**: 73개 (Vitest), 전부 통과
- **타입 체크**: tsc --noEmit 오류 없음
- **빌드**: Vite 프로덕션 빌드 성공

## 🎮 방해요소 5종 설계 명세

| 요소 | 규칙 |
|------|------|
| **콘크리트** | 내부 빈칸 생성. HP 3. 충돌 시 HP -1. HP 0이면 파괴. 움직이지 않는 벽. |
| **% 블럭** | 내부 빈칸 생성. 충돌 블럭 값 절반(÷2). 1은 유지. 발동 후 제거. |
| **얼음** | 병합 결과 블럭 중 랜덤 선택. 3턴간 고정 벽. 해동 후 일반 블럭. |
| **포탈** | IN/OUT 쌍. 외곽 좌표(x=-1, x=size, y=-1, y=size)에 생성. IN으로 들어간 블럭이 OUT에서 FIFO 큐로 방출. |
| **컨테이너** | 내부 빈칸 생성. 방향값 가짐. 충돌 블럭들을 지정 방향으로 재방출. 발동 후 제거. |

### 설계 제약
- 컨테이너 ↔ 포탈/컨테이너/%/콘크리트/얼음 연쇄 상호작용 금지 (벽처럼 처리)
- 여러 컨테이너 연쇄 발동 금지
- 얼음은 충돌로 HP 깎이지 않음
- OUT 방출 경로 막히면 큐 유지 (손실 금지)
- OUT→IN 즉시 재진입 루프 금지
- 모든 방해요소는 성공한 스와이프 후 PLACE 단계 직전 1회만 등장 판정
- 한 번에 1종류만 생성 (포탈은 IN/OUT 쌍)
- MAX_ACTIVE_OBSTACLES = 2

## 🔍 분석 관점 (모든 관점에서 평가해주세요)

### 1. 🎯 사용자 관점 (UX/UI)
- 방해요소가 숫자 타일과 **충분히 구별**되는가?
- 각 방해요소의 **아이콘/심볼이 직관적**인가? (처음 보는 사용자 기준)
- **정보 가독성**: HP, 남은 턴 수, 방향 등이 충분히 크고 읽기 쉬운가?
- **피드백**: 방해요소 등장/파괴/발동 시 시각적 피드백이 충분한가?
- **모바일**: 4x4~10x10 다양한 보드 크기에서 UI가 깨지지 않는가?
- **색맹**: 색상만으로 구분해야 하는 요소가 있는가?
- **프리미엄 스킨**: 어두운 테마(Galaxy, PixelBlast)에서도 방해요소가 잘 보이는가?
- **게임 흐름**: 방해요소가 게임의 리듬을 과도하게 방해하지 않는가?

### 2. 🏗️ 개발자 관점 (코드 품질/아키텍처)
- **모듈 분리**: obstacleEngine.ts ↔ gameLogic.ts 분리가 적절한가?
- **함수 크기**: slideGridWithObstacles(874행) 등 대형 함수의 분할 필요성
- **상태 관리**: ObstacleState의 불변성, cloneObstacleState 패턴이 안전한가?
- **타입 안전성**: any 타입 사용, 타입 단언(as) 남용 여부
- **에러 처리**: 예외 상황(손상된 상태, 경계 조건)에 대한 방어 로직이 충분한가?
- **중복 코드**: 유사한 로직이 여러 곳에 분산되어 있는가?
- **네이밍**: 변수/함수명이 의도를 명확히 전달하는가?
- **주석**: 복잡한 로직에 충분한 설명이 있는가?

### 3. 🐛 버그 탐색 (Edge Cases)
다음 시나리오에서 버그 가능성을 검토해주세요:
- **동시 발동**: 컨테이너 + 포탈이 같은 스와이프에서 발동할 때
- **부분 발동**: 컨테이너가 일부 타일만 리디렉션할 때 (보드 공간 부족)
- **포탈 큐**: 큐가 가득 찼을 때, OUT 경로가 완전히 막혔을 때
- **얼음 + 병합**: 얼어붙은 타일이 병합 대상이 될 때
- **MAX_ACTIVE_OBSTACLES 경계**: 정확히 2개일 때 새 방해요소 스폰 시도
- **보드 크기**: 4x4, 7x7, 10x10 각각에서의 동작 차이
- **Undo/Redo**: 방해요소 상태가 정확히 복원되는가?
- **저장/복원**: 구버전 세이브 데이터 로드 시 호환성
- **게임오버 판정**: 방해요소로 인해 canPlace=true, canSwipe=false인 soft-lock 상황
- **Pity 시스템**: spawnMissStreak 오버플로우, 음수값

### 4. ⚡ 성능 관점
- **렌더링**: ObstacleLayer, PortalMarkers의 React.memo 사용 적절성
- **useMemo/useCallback**: 불필요한 재계산 방지
- **DOM 조작**: hiddenTileIds로 인한 불필요한 DOM 생성/소멸 여부
- **애니메이션**: obstacleDropImpact, obstacleImpactRing의 성능 (will-change, transform 사용)
- **번들 크기**: obstacleEngine.ts(1,150행)가 번들에 미치는 영향

### 5. 🔒 보안/데이터 무결성
- **localStorage**: 저장된 게임 상태의 무결성 검증
- **obstacleRulesVersion**: 버전 불일치 시 마이그레이션 안전성
- **치트 방지**: 클라이언트 상태 조작으로 인한 취약점
- **XSS**: 사용자 입력이 렌더링에 사용되는 경로

### 6. ♿ 접근성
- **aria 속성**: ObstacleLayer의 aria-hidden 사용 적절성
- **키보드 네비게이션**: 방해요소가 키보드 플레이를 방해하지 않는가?
- **prefers-reduced-motion**: 애니메이션 비활성화 대응
- **스크린 리더**: 방해요소 정보가 음성으로 전달될 필요가 있는가?

### 7. 🧪 테스트 커버리지
- 현재 73개 테스트로 충분한가?
- 누락된 테스트 시나리오는 무엇인가?

## ⚠️ 중요 컨텍스트

1. 이 게임은 **프로덕션 배포 중인 실서비스**입니다. 회귀(regression)가 발생하면 실제 사용자에게 영향이 갑니다.
2. 방해요소 시스템은 **기존 게임 로직(gameLogic.ts)을 수정하지 않고** 독립된 엔진(obstacleEngine.ts)으로 추가되었습니다.
3. **프리미엄 스킨**(Win98, Galaxy, PixelBlast, Neon Block)과의 호환성이 중요합니다.
4. **iOS/Android 모바일** 환경에서 Capacitor를 통해 네이티브 앱으로도 배포됩니다.
5. **저장/복원** 호환성: 구버전 세이브 데이터를 불러올 수 있어야 합니다.
6. 최근 UI 개선으로 **이모지(🛡️✂️) → SVG 아이콘** 교체, **얼음 디밍 완화**, **%블럭 ÷2 심볼** 변경이 적용되었습니다.
